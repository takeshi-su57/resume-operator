# How to Use

End-to-end walkthrough of resume-operator. Two surfaces share one engine — the [CLI](#cli-walkthrough) (Typer + Rich) and the [desktop app](#desktop-app-walkthrough) (Tauri 2 + React). Both invoke the same compiled LangGraph and the same flows behind a `Prompter` seam, so the choice is purely about UX preference.

For the system architecture (data flow, conditional routing, server layer), see [`docs/architecture.md`](../architecture.md). For the iterative approval loop's design, see [`iterative-tailor-approval.md`](iterative-tailor-approval.md).

---

## One-time setup

Before either surface works, you need three things in place: the engine installed, an LLM API key, and a master resume YAML.

### 1. Install the engine

```bash
git clone <repo-url>
cd resume-operator
uv sync --dev
cp .env.example .env
# Edit .env — at minimum set LLM_PROVIDER and the matching API key
```

You only need **one** API key — the one matching your chosen `LLM_PROVIDER` (`openai`, `anthropic`, `google`, or `openrouter`).

### 2. Bootstrap your master resume

`master_resume.yaml` is the hand-maintained source of truth. Bootstrap once from your existing PDF, then maintain by hand:

```bash
uv run python -m resume_operator bootstrap \
  --resume my-existing-resume.pdf \
  --output data/master_resume.yaml
```

The command parses the PDF with the LLM, then walks an interactive interview asking for the senior-format fields the parser couldn't recover (headline, Portfolio / LinkedIn / GitHub URLs, per-role tech stacks, a categorised skill grouping). Hit Enter at any prompt to skip; pass `--no-interview` to skip the whole interview.

Open the produced YAML, verify it matches your résumé, and edit freely. The agent never writes back to it — every accepted change lands in `data/facts_bank.yaml` instead, with an `overrides:` pointer when it polishes a master bullet.

### 3. (Optional) Maintain a facts bank

`data/facts_bank.yaml` is a separate pool of items that don't fit on the trimmed master but might still be relevant for some JDs. Two ways to grow it:

- **Hand-edit** — see [`input/facts_bank.example.yaml`](../../input/facts_bank.example.yaml) for the schema.
- **Auto-enrich** — when a tailoring run comes back thin, `run` pauses and offers an interview. The LLM asks grounded questions, you answer in plain prose with facts and metrics, the LLM polishes to ATS bullets, you accept / edit / reject each one. Accepted items append to `facts_bank.yaml` durably across sessions.

## CLI walkthrough

### Tailor a resume — `run`

The default command. Loads master + JD → multi-dim ATS score → if below threshold, analyse gaps → tailor content → score the tailored output → enter the approval loop → finalize (PDF + diff + results JSON).

```bash
uv run python -m resume_operator run \
  --master data/master_resume.yaml \
  --job input/job.txt
```

Output lands in `data/applications/{YYYY-MM-DD}_{slug}/`:

```
data/applications/2026-04-27_acme-senior-eng/
├── resume.pdf       ← rendered tailored resume
├── results.json     ← structured run report (ATS, gaps, decisions)
├── tailored.yaml    ← serialized TailoredResume
└── diff.md          ← human-readable per-item before/after
```

The slug is derived from the JD's company / filename / a hash of the JD text. Collisions append `-2`, `-3`, etc. — runs never overwrite each other.

#### Common `run` flags

| Flag | Effect |
|---|---|
| `--facts <yaml>` | Load a facts bank (defaults to `data/facts_bank.yaml` if it exists). |
| `--style <yaml>` | Apply a StyleTemplate (#037). Generated by `extract-style` from a reference `.docx`. |
| `--max-iter N` | Cap on the approval loop (default 3). After N rejections, you get a "continue anyway?" prompt. |
| `--no-approve` | Skip the approval loop entirely; render the first tailored version. |
| `--no-enrich` | Skip the auto-enrichment offer even when the tailor is thin. |
| `--output <dir>` | Override the parent of the per-application folder (default `data/applications/`). |
| `--verbose` / `-v` | Enable DEBUG logging. |

### What the approval loop looks like

After each tailor pass you see:

```
Iteration 1/3: ATS score on tailored output = 64%
Accept this tailored version and generate the PDF? [y/N]:
```

- **Accept** → finalize and write the PDF.
- **Reject** → the LLM emits up to 5 grounded proposals. Each goes through a Yes / No / Fix gate.

For each proposal you see a panel showing the kind (rewrite_master / rewrite_fact / new_fact / new_skill), the grounding source ID, the original (if any), the proposed text, and the LLM's rationale. You answer:

```
[Y]es / [N]o / [F]ix — give feedback, LLM revises / [q]uit (y):
```

- **`y`** — approve. Lands in `facts_bank.yaml` with an `overrides:` pointer when polishing an existing master bullet.
- **`n`** — reject. Optional reason captured ("I never used K8s, only ECS"); the LLM avoids the same idea on the next iteration.
- **`f`** — fix. Free-text feedback → LLM revises → you see v2 on the same gate. Unbounded.
- **`q`** — quit the approval loop. The best-scoring iteration seen is rendered.

When approvals land, the next iteration's tailor pass sees the enriched facts bank and produces a new tailored version with a fresh ATS score.

### Auto-enrichment

If the first tailor pass keeps fewer items than `ENRICH_THRESHOLD` (default 6), `run` pauses and asks:

```
Enrichment available
Only a few items landed in the tailored resume — your master + facts may
be thin for this JD. We can grow your facts bank with a short interview
now (LLM asks grounded questions, you answer in your own words, LLM
polishes the phrasing).

Start an enrichment session? [y/n] (y):
```

Accept and the LLM produces up to 5 questions targeted at gaps:

```
Question 1/5: At TechCorp, what was the scale of the backend system?
why: JD emphasizes scalable backend work.
Answer with facts and metrics (e.g. "I built 50+ endpoints serving 2M
requests/day"). Do NOT type instructions like 'make it professional' —
that's the LLM's job in the polish step.
> _
```

You answer in plain prose. The LLM polishes to an ATS bullet and shows the bucket classification (project / extra_bullet / skill / certification) and role linkage:

```
Polished:  → extra_bullet (role_id=exp-1)
  Designed RESTful API for 50+ endpoints at TechCorp, cutting p99
  latency 30% via Redis caching.

[a]ccept / [e]dit / [r]eject / [s]kip / [q]uit (a):
```

Accepted items append to `facts_bank.yaml`. After enrichment finishes, the graph re-invokes once with the enriched facts so `optimize_content` sees them.

### Score-only — `score`

```bash
uv run python -m resume_operator score \
  --master data/master_resume.yaml \
  --job input/job.txt
```

Multi-dim ATS report only — no tailoring, no PDF write. Useful for inspecting how your master scores against a JD before committing to a full run. Output is a Rich table covering composite, structural checks (contact info / sections / job-title match / measurable results / word count), per-skill tables for hard and soft skills (resume-vs-JD counts), and tone flags.

### Inspect a PDF — `parse-resume`

```bash
uv run python -m resume_operator parse-resume --resume some-resume.pdf
```

Shows what the LLM would extract from a PDF — name, email, phone, skill list, counts. Read-only; doesn't write any YAML. Useful before deciding whether to bootstrap.

### Derive a style — `extract-style`

```bash
uv run python -m resume_operator extract-style \
  --from reference-cv.docx \
  --output data/my-style.yaml
```

Reads a reference `.docx`, extracts its named styles (font family, margins, font sizes for name / section / body), and writes a StyleTemplate YAML. Apply with `run --style data/my-style.yaml`. Edit the YAML by hand to fine-tune anything the extractor missed.

## Desktop app walkthrough

The desktop app exposes every CLI command as a screen, plus a home dashboard and a `cmd/ctrl+K` command palette. The crown-jewel screen is **Run** — the iterative approval loop becomes a side-by-side workspace where every decision has full context on screen.

### Launching dev mode

```bash
# Terminal 1 — engine
uv run resume-operator-server

# Terminal 2 — Tauri shell
cd desktop
pnpm install     # first time only
pnpm tauri:dev
```

The window opens against Vite's `localhost:1420`; HTTP/WebSocket calls hit the engine on `127.0.0.1:7421`. Sett the engine offline (kill the terminal) and the top-bar status pill turns red — useful for confirming everything's wired right.

### The screens

#### Home

Engine status banner (online with provider/model, or offline with the sidecar-start hint) plus a 3×2 grid of tile shortcuts. "Tailor a resume" is the primary tile (accent-tinted); the others are secondary.

#### Settings

Every env var from `config.py` exposed as a form:

- LLM provider + model
- Four API keys — masked on read (`sk-p…7890`); type a new value to replace
- Log level, ATS skip threshold, enrich threshold, max approval iterations, resume style path
- The six ATS composite weights (#042) — server caps each at [0, 1]

Save persists to `.env` in the project root and invalidates the cached settings — next request picks up the new values. Reset discards unsaved edits.

#### Score

Two file pickers (master YAML preferred, legacy resume PDF fallback) + job description text → submit → multi-dim ATS report on the right pane.

The report mirrors what the CLI's `score` command prints, in a denser layout:

```

   ─────
   composite reasoning

   ✓  Sections           all present
   ✓  Job title match    'Senior Backend Engineer' exact match
   ✓  Measurable results 11 quantified lines
   ⚠  Word count         1188 words (target 400-1000)

HARD SKILLS                       SOFT SKILLS
  Skill        Resume   JD          Skill          Resume   JD
  RESTful API     1     1           Communication     0     1

  "passionate"     — Show passion via measurable contribution

```

#### Run — the three-pane workspace

Left rail picks inputs (master / resume / job / facts / style + advanced flags). Submit transitions into the workspace:

```
┌──────────────┬───────────────────────────────────┬───────────────────┐
│ NODE TIMELINE│ CURRENT PROPOSAL  1/5  [rewrite]  │ SESSION           │
│ ◉ load_master│ master:exp-2-b3                   │                   │
│ ◉ ats_score  │                                   │ ATS score         │
│ ◉ analyze    │ - Built scalable API              │   78%             │
│ ◉ optimize   │ + Scaled Go API to 10k req/s     │                   │
│ ◎ ats_tailor │   with Redis caching              │ Iteration         │
│ ○ approve ←  │                                   │   2 / 3           │
│ ○ finalize   │ Rationale: JD emphasizes scale…   │                   │
│              │                                   │ Decisions         │
│ Iterations   │ [Accept ⏎] [Reject x] [Fix… f]    │   Approved   3    │
│ iter 1  64%  │                          [Quit q] │   Rejected   1    │
│ iter 2  78%  │ ──●─────────  4 remaining         │   Enrich     0    │
│              │                                   │ ↻ LLM proposing…  │
└──────────────┴───────────────────────────────────┴───────────────────┘
```

- **Left** — live node timeline. Lights up green / cyan / grey as the graph runs. Iteration history below tracks ATS climbing or regressing.
- **Center** — current decision. For proposals: kind label, grounding source, word-level diff (red strikethrough for removed text, green highlight for added), rationale, action row. For iteration confirmations: open question + ATS context + Yes/No.
- **Right** — running session: current ATS, iteration progress, decision counts, open status spinner.

**Keyboard shortcuts** (scoped to the approval phase, disabled when an input or modal has focus):

| Key | Action |
|---|---|
| `Enter` | Accept proposal |
| `x` | Reject (opens reason modal — empty reason fine) |
| `f` | Fix (opens textarea — Ctrl+Enter submits) |
| `q` | Quit approval loop (server returns the best-scoring iteration seen) |
| `←` `→` | Navigate proposals |

When the run finishes, the center pane shows a Done panel with the output PDF path and a "Show in folder" CTA that opens the parent directory in Explorer / Finder.

#### Run — enrichment phase

When the tailor comes back thin, the enrichment offer appears as an iteration-confirm card. Accept to enter the interview:

- **Question card** — question + why + textarea for your free-text answer. Polish (Ctrl+⏎) sends; Skip / Quit available.
- **Polished card** — bucket badge (project / extra_bullet / skill / certification), role_id chip if applicable, polished text in a green-tinted block. Keyboard: `a` accept, `e` edit (expands an inline textarea pre-filled with the polished text — Ctrl+⏎ saves), `r` reject, `s` skip, `q` quit.

Accepted items append to `facts_bank.yaml`. After the session, the workspace transitions back into the approval loop with the enriched facts loaded.

#### Bootstrap

PDF + output path + skip-interview flag → `WS /api/ws/bootstrap` → activity log and prompt panel render the senior-format interview (headline / links / per-role tech / skill grouping). On done, a green output-path footer with the YAML you can hand-edit.

#### Parse PDF

Single PDF picker → fields panel showing extracted name / email / phone / summary / skills + counts. Read-only inspector.

#### Extract Style

`.docx` picker + optional output YAML path → preview panel showing font family, margins, three font sizes. When output is set, a green "wrote …" banner confirms the YAML.

#### Cmd-K

Press `cmd/ctrl+K` from any screen to open a Linear-style command palette. Phase 5 ships navigation only — one entry per screen. Arrows + Enter to navigate; Esc to close.

## Programmable surface

The `resume-operator-server` engine is a peer to both the CLI and the desktop app. Anything the CLI does, you can drive over HTTP or WebSocket from your own scripts.

```bash
# Boot the engine
uv run resume-operator-server --port 7421

# Score a resume
curl -X POST http://127.0.0.1:7421/api/score \
  -H "Content-Type: application/json" \
  -d '{"master":"data/master_resume.yaml","job":"input/job.txt"}'

# Read or update settings
curl http://127.0.0.1:7421/api/settings
curl -X PUT http://127.0.0.1:7421/api/settings \
  -H "Content-Type: application/json" \
  -d '{"llm_provider":"anthropic","llm_model":"claude-sonnet-4-6"}'
```

For interactive flows (`/api/ws/run`, `/api/ws/bootstrap`), open a WebSocket, send `{"type":"start","params":{...}}`, then respond to the server's `confirm` / `choose` / `text` / `render_proposal` / `render_question` / `render_polished` messages with `{"type":"reply","value":...}`. The protocol mirrors the `Prompter` seam the CLI's `RichPrompter` and the desktop's `WebSocketPrompter` both implement — see [`src/resume_operator/server/ws_prompter.py`](../../src/resume_operator/server/ws_prompter.py) for the message shapes.

## Troubleshooting

| Symptom | Cause + fix |
|---|---|
| `"OPENAI_API_KEY not set"` | Your `.env` is missing the key, or you set the wrong provider. Run the CLI once to confirm; fix `.env` and retry. |
| `"PDF has no extractable text"` | The PDF is image-based. Run it through OCR first (e.g. ocrmypdf). |
| Desktop top-bar shows "engine offline" | The sidecar isn't running. In dev mode, start `uv run resume-operator-server` in another terminal. |
| `pnpm tauri:dev` errors with `link: extra operand …rcgu.o` | MSVC's `link.exe` is shadowed by Git's GNU coreutils `link`. Install Visual Studio's "Desktop development with C++" workload via VS Installer. |
| Approval loop won't fire | You passed `--no-approve`, or stdin isn't a TTY (CI environment). Approval-loop tests use `--no-approve` deliberately. |
| Enrichment offer never appears | Either the tailor didn't come back thin (kept ≥ `ENRICH_THRESHOLD` items, default 6), or you passed `--no-enrich`. Lower the threshold via env var to test. |
| Run a previous application's outputs | Each run writes into `data/applications/{date}_{slug}/`. Open the folder; `resume.pdf` is the rendered output, `diff.md` is the human-readable per-item diff, `results.json` is the structured report. |
